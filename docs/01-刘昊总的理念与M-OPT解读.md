# 刘昊总的理念与 M-OPT 解读

> 定位：读懂 M-OPT 在解决什么组织问题，以及它与此前 185 体系的关系。
>
> 日期：2026-09-05｜版本：v0.1｜性质：材料解读，供内部讨论。
>
> 阅读顺序：本篇理解理念；[第二篇](./02-EVA×OCTO融合产品战略背景与产品哲学基底-POC提案.md)讨论融合产品与 POC 如何落地。

## 一、先用一句话理解 M-OPT

**M-OPT 希望让每个自然人带着一套分工清楚的 AI 小队承担工作，再让这些“人 + AI 小队”在组织里协作**。

它想改变的，是企业分配工作时默认面对的那个单位。

过去把一项工作交给小王，主要依靠小王本人完成。M-OPT 下仍然由小王接收目标、判断结果、对交付负责，但他身后有助理处理准备工作，有专业能力完成领域任务，还有分身替他接住协作请求、跟进流转。

小王和小李合作时，双方不必亲自完成每次传话、找资料和状态确认。各自的小队可以在授权范围内协同，需要决策时再回到人。

这就是 OPT 和 M-OPT 的关系：

| 名称 | 白话解释 | 关注的问题 |
| --- | --- | --- |
| OPT，One-Person Team | 一个人带着自己的 AI 协同体系工作 | 我如何借助 AI 完成一件事 |
| M-OPT，Multi-One-Person-Team | 多个这样的人机单元相互协作 | 很多个“我”如何一起完成组织的事 |

“单人”指单元的责任中心是一个自然人，不代表每项业务都不再需要其他人。“多”既指多个单元组网，也包含一个人服务多个业务域、能力被多个单元复用。[M，第 1—2 页]

文档中“单人即可完成全链路业务交付”是一种目标描述。一个 OPT 是否真的具备完整交付能力，仍取决于业务范围、已有能力、数据和系统条件，不能由名称直接推出。

## 二、先有 185，后有 M-OPT：理念如何向前推进

按本次提供的时间关系，先有 2026 年 8 月 6 日的 185 白皮书、蓝皮书，后有 M-OPT V1.4。解释同一角色时，以后者的明确规定为主；后者未展开的实施与运营问题，可以回到 185 寻找背景。

这种优先级用于理解刘昊总的理念演进，不代表 M-OPT 已自动替代双方评审过的全部产品与工程约定。

### 2.1 185 先回答：企业怎么把 AI 系统性地用起来

185 的三个数字分别对应：

- **一张网**：让人、AI、业务系统能够发现彼此、交换信息、协作执行。

- **八步落地**：明确目标、识别场景、重塑流程、规划资源、改造系统、治理数据、选择模型、迭代运营。

- **五个机制**：信息自动汇聚、任务自动路由、意图一次说清、事情并行干、经验自动沉淀。

这套体系关心的是组织效果。接入 AI 后，是否少找几次人、少传错一次要求、少重复做一次工作，成果是否更快、更好，经验是否留下来了。其评价包含价值、成本、质量、体验、安全，并强调“三分建设，七分运营”。[W，第 2—6 页；B，第 3—6 页]

### 2.2 M-OPT 进一步回答：网上的每个协作单元应该怎样组成

只有“一张网”还不够。人和很多 Agent 连上以后，仍然可能出现以下问题：

- 同一项工作被几个 Agent 重复执行。
- 不清楚一个 Agent 代表谁、能答应什么。
- 管理者同时参与多个项目，信息和权限混在一起。
- 人人重复建设相似的专家，企业能力无法复用。
- 结果出了问题，无法追到具体的人、业务域与执行能力。

M-OPT 用角色分工、业务域隔离、能力池与责任追踪来回应这些问题。

可以把两份体系的关系理解为：**185 描述组织要怎样运转，M-OPT 规定参与运转的单元如何组成、如何交接**。这是本文的综合判断，而非两份文档已经共同发布的一套合并定义。

### 2.3 最容易误读的变化：前后两版的“分身”不是同样宽的概念

185 的“分身型 AI”可以持续记忆、主动规划、调用工具、派生并行任务、跟进工作，范围很宽。M-OPT V1.4 的“对外分身”只保留通信、契约、路由与治理，不做业务推理和内容生成。[B，第 3—4 页；M，第 4 页]

因此不能直接把早期分身的全部能力搬到新版分身里。更合理的理解是：早期分身帮助一个人完成工作的那套能力，在新版中被拆分给了整个 OPT。

同样，185 的“工具型 / 流程型 / 分身型”偏向 AI 的工作方式；M-OPT 的“助理 / 分身 / 专家”偏向组织中的职责位置。两套分类不能逐项等号对应。

## 三、拆开 1:N:M：到底是谁、有什么、归谁管

V1.4 的结构可以写成：

> 一个自然人，配一个全局对内助理；按业务域拥有 N 个对外分身；每个业务域选配 M 个专家能力。

这里的 M 不必每个域相同。专家来自共享资产池，同一项能力可以被不同业务域选用。公式表达的是归属与选配关系，不是必须启动多少个常驻进程。[M，第 2—3 页]

| 组成 | 它负责什么 | 它不应越过的边界 |
| --- | --- | --- |
| 自然人 | 判断业务目标、作出决策、终审成果 | 不能因 AI 执行而让业务责任变得无人承担 |
| 对内助理 | 整理材料、处理个人事务、拆解准备工作、汇聚个人记忆 | 不独立对外承诺，不承担专业业务终审 |
| 对外分身 | 代表某人在某个业务域接收请求、校验权限、路由、回传与留痕 | 不独立作业务判断，不生成或改写业务结论 |
| 领域专家 | 根据专业规则进行推理与执行，产出结构化初稿 | 不独立对外通信，不越过授权范围，不把初稿当最终决定 |

### 3.1 一个人只有一个助理，为什么又可以有多个分身

助理面向“我自己”。文档希望一个人有一个稳定的私有工作入口，不因换项目就另起一套个人体系。

分身面向“我在这个业务里代表谁、可以说什么”。同一个管理者在产品研发、供应商合作、内部经营等场景中，面对的人和可披露的信息不同，所以需要不同业务域分身。

这并不意味着全局助理可以把所有项目记忆混在一个上下文中。V1.4 同时要求它处理跨域事务时带上域标签、分片存储。**统一的是个人入口，分开的是不同业务的工作上下文**。[M，第 2、3 页]

### 3.2 业务域是什么，与项目有什么区别

业务域可以先理解成：**一组有明确职责、对象和信息边界的工作**。

例如“某车型研发项目”可以形成一个域，“与某供应商的合作”也可以形成一个域。V1.4 允许按项目、业务线、合作生态创建分身，因此业务域并不天然等于项目，也不等于部门或一个聊天群。

项目主要组织目标与交付，业务域主要约束身份、权限和信息使用。两者具体是一对一还是一对多，原文没有给出统一规则。产品需要补充定义，不能直接假定“建一个群就自动获得一个业务域”。

### 3.3 专家是公司共有的，为什么还能叫“我的团队”

“我的”指我可以调用哪些能力，不等于这些能力资产归我所有。

公司可以有一套统一维护的质量分析专家。小王的车型研发域、小李的售后质量域都可以选用它，但每次调用只能使用本次获准的数据。复用的是专业能力，不是前一个项目的会话和记忆。

V1.4 规定企业资产团队负责专家建设、版本迭代、灰度发布和回归管控，员工只做域级选配。这把“谁维护能力”和“谁用能力交付”分开了。[M，第 3—4 页]

### 3.4 有 IM 身份，为什么又说没有独立账号

一个分身可以有可见名称、技术标识、会话和审计记录，让别人准确找到它。但它的权限和业务责任依附于自然人，不能自己获得一套脱离主人的权力。

所以，“可区分的技术身份”与“独立的用户账号或业务权责主体”需要分开理解。原文同时使用“独立 IM 身份”和“无独立账号”，应在这个层次上解释，不能据此省略技术 ID 与审计对象。[M，第 1—2、5 页]

## 四、用一件事看它怎样工作

下面是帮助理解的示例，不是白皮书中的业务案例，也不代表已经选定为本项目的 POC 场景。

小李希望小王在周五前提交一份质量问题分析。

1. **请求进入对应分身**。小李在获准协作的场景里找到“小王 · 车型研发域分身”。请求中说明问题、材料、期限与希望拿到的结果。

2. **分身判断能不能接、交给谁**。它检查请求是否属于这个域、资料是否可用、是否需要小王先确认；不自己开始推导质量结论。

3. **助理或专家处理工作**。整理附件、归集素材可以交给助理；专业原因分析交给域内获准的质量专家。真实工作可先准备材料再分析，不必把每项复杂工作硬分成只能走一个分支。

4. **小王审阅结果**。专家提供初稿和证据，小王判断是否成立，必要时要求修改。具体哪些任务逐项审核、哪些低风险动作可预授权，需要产品规则明确。

5. **分身回传获准发布的成果**。回传时关联原请求、版本与执行来源。对外脱敏若改变了业务含义，需要再确认，不能借“治理”悄悄重写结论。

6. **留下一条完整记录**。能够追到负责的人、工作的业务域、调用的专家，以及最终交付的成果。

当小李也由自己的分身接收回执、跟进状态时，就是两个 OPT 之间的协作。其价值在于减少人反复传话与整理的负担，同时保留业务决策的位置。

这里的“契约”先理解为双方对工作内容、边界与交付的约定，不必理解为一份法律合同。V1.4 给出了契约管理的职责，但没有给出完整字段、接受机制、变更流程和状态机。这些是后续标准与产品需要补齐的部分。[M，第 4—6 页]

## 五、为什么专家不进群，也不妨碍人机协同

V1.4 明确规定：组织通信中，只有分身可进群、建群、被 @；助理和专家没有独立的对外社交身份。[M，第 5 页]

这意味着用户看到一个专家的执行过程，并不必然意味着专家是群成员。产品可以在个人工作台中展示它的任务、进度、分析结果，再由分身或经本人确认的发布操作把结果送到协作场景。

因此，“我的团队”可以是一种个人工作体验，不一定是把所有 Agent 拉进一个组织 IM 群。

这也是新材料对 0904 周会分析的一次修正：周会中有“专家进我的团队群”“分身永远一个”“我的几个助理”等表述，V1.4 已给出不同规定。按本次阅读优先级，应以 V1.4 理解最新理念；这些差异仍需在产品评审中明确替换关系，不能把前后材料拼成互相矛盾的一组要求。

## 六、刘昊总真正想约束的，是组织如何运行

把 185、周会发言和 M-OPT 放在一起，可以看到几条持续出现的关注点。

### 6.1 人机分工必须足够清楚

分工混乱会带来重复执行、重复消耗、责任模糊。M-OPT 用三类角色回应这个问题。分身“少干活、多传话”在 V1.4 中被进一步收紧为治理与路由职责。

但角色分工只能减少职责重叠，不能自动消除重复任务。同一个请求被重复发送，两个专家仍然可能做两遍。产品还需要任务关联、重复识别和成果版本管理。

### 6.2 协作要围绕一个能持续跟踪的意图

185 的“意图一次说清”，希望目标在传递和执行中不丢失。M-OPT 的“契约”给它找到了一个更明确的承载方式。

这要求系统记住最初要什么、谁承接、什么时候交、什么算完成。只保存聊天记录还不够，只有任务卡片也不够；要把请求、执行和验收联系起来。

### 6.3 每个人变强以后，还要能形成组织的复用能力

一人完成得好，只验证了个体能力。多个 OPT 能协作、专家资产能被不同域复用、成功经验能改善后续执行，才接近组织范式。

M-OPT 将组织级自学习放在更后的演进阶段。不能把“将来自动萃取”解释为当前已经能自动获得高质量、可复用的组织知识。[M，第 7—8 页]

### 6.4 要知道它有没有价值，不能只知道它有没有运行

185 讨论持续运营；0904 周会进一步要求记录消耗、结果与反馈，分别评价助理、分身和数字员工，提出 IR（Intelligence Resource）管理。[W，第 4—6 页；T，50:30—57:45]

可以据此推导：助理要看准备工作是否省时、准确；分身要看请求是否接对、转准、跟进完整；专家要看成果质量与返工情况。这些是建议的评价方向，材料尚未给出三类角色统一定稿的指标公式。

## 七、文档还没有替产品回答的几件事

“终极定稿”“永久不变”是原文对自身版本的表述。阅读时要同时区分：明确的理念、尚需解释的规则、未经验证的效果承诺。

| 原文表述 | 可以读出的意图 | 仍需补齐的问题 |
| --- | --- | --- |
| 助理零对外网络权限，专家禁止直接外联 | 防止私有能力绕过授权和发布出口 | 是否允许受控模型调用、检索和业务工具访问；“对外”指组织通信还是所有网络 |
| 多域完全隔离，未来又支持跨域租借 | 默认限制信息与能力跨域流动 | 授权后的交换和租借怎样发生；共享资产与共享运行数据如何区别 |
| 人拥有终审权，高风险直接路由人 | 决策与风险控制回到人 | 普通专业成果在哪一步审核；日常低风险操作可否预授权 |
| 分身不改写内容，又负责脱敏 | 保持业务结论来源，控制披露 | 脱敏改变含义时谁复核；传输格式转换与内容修改如何区分 |
| 任务零重叠 | 同一交付不要无谓重复 | 任务去重、重试、唯一成果、并行分工如何实现 |
| 全链路三元组：自然人、域分身、领域专家 | 责任与执行可追溯 | 助理执行、人工执行、多个专家执行时如何记录，不能填一个虚构专家 ID |
| 专家只能统一建设，组织以后自动萃取能力 | 正式能力需要质量与版本治理 | 员工的新方法如何成为候选、如何评审发布；自动候选何时成为正式资产 |

同样，业务域标签并不自动等于物理隔离，共享同一模型也不等于共享会话。实际边界要由权限校验、上下文装配、存储访问和执行环境共同兑现。

原文关于自然人承担法律责任的措辞，本文只作为其权责设计主张转述。产品应记录真实责任链，不能用一个字段替代具体的责任认定。

## 八、读完以后，应该带走什么

M-OPT 的核心画面是：**一个人有自己的内部工作体系，按不同业务身份对外协作，调用组织提供的能力，最后把判断与责任交回人。多个这样的单元连起来，组织才可能持续交付和进化**。

理解它不需要先背住所有 Agent 名称。先问四件事就够了：

1. 这件事最终由哪个人负责？
2. 他现在以哪个业务身份、在什么授权范围内工作？
3. 谁提供专业能力，谁负责对外协作？
4. 结果如何被确认，经验如何改善下一次工作？

对 EVA × OCTO 融合而言，下一步是把这些问题变成稳定的产品规则，再挑一个足够小的业务范围验证。哪些规则 POC 必须落实、哪些能力可以后置，见[第二篇](./02-EVA×OCTO融合产品战略背景与产品哲学基底-POC提案.md)。
