# AI 开发与合并验收规范

## 开始修改之前

必须先阅读根目录 AGENTS.md、CONTRIBUTING.md、本文件，以及改动业务对应规范。身份入口读 AI 身份合同；IM 读内核与触发规则；任务读《会话内项目任务规范》；个人 UI 读 GDS README、design.md、tokens、components 及对应参考图。只读文件名、搜索片段或依赖旧对话不算完成阅读。

开工说明必须简述：适用规范、已确认产品规则、要保留的行为和本次改动范围。规范之间存在矛盾时先核对用户最新决定；不能自行选择最方便的一条。技术性修复无需重复问用户，新的产品取舍必须确认。

## 合并与恢复

1. fetch 后记录基线 main、来源分支、目标分支的提交 SHA；修改前确认工作区归属。
2. 按能力对照已发布版本、来源分支、整合结果。缺失代码不代表同事有意删除：未明确改动的能力保留已发布行为。
3. 明确区分用户认可的新设计、遗漏同步、有意删除、实现缺陷。不能把所有差异都称作冲突。
4. 冲突逐段解决；禁止不看内容就整文件选 ours/theirs。两边独立修复都应保留，无法兼容的产品选择才交用户判断。
5. 恢复旧组件时同时检查 DOM 结构、CSS 类名、事件监听、路由、数据源、入口与 manifest；不能仅恢复 JS 或 CSS 就宣称完成。
6. 远端 main 在工作期间更新时，重新对照其增量；不得用本地旧文件抹掉他人后续修复。

## 必须保持的行为

- 我的 AI 展示云端分身、个人助理与数字员工。个人助理名称与个人 Eva 同步；IM 会话与个人本地聊天记录、草稿隔离。
- AI 标使用公共组件，紧跟名称；长名截断不得把标记推到行尾。AI 的单张圆形头像尺寸与裁切由公共身份 CSS 控制，禁止广泛 img 选择器覆盖头像。
- 通讯录优先一行展示真人头像、姓名、部门和所属分身，真人与分身之间用短竖线区分；不得将部门、分身数量和分身列表拆成多层纵向标题。1～6 个分身按实际内容宽度紧凑横排，仅空间不足时在分身区换行；超过 6 个原组内展开／收起，搜索直接展示折叠命中项。
- 项目设置编辑表单与项目概览使用不同根类名；标签、输入框、说明与保存按钮必须成组排列，保存仍作用于当前项目。
- 历史栏识别必须使用业务标识，禁止仅凭 overflow、flex 等布局类识别并隐藏容器；一级导航不得被历史栏脚本隐藏。
- 会话任务保留完整项目前缀、当前项目权限与数据隔离；界面文件存在不等于运行时已经接入。
- 演示状态不代替正常输入、编辑、粘贴与会话数据流程。不能把任意请求都转换成同一个固定结果。
- 用户认可布局，不等于同意更改身份边界、权限、数据持久性或全局设计 token。GDS 适用范围按项目规范执行。

## 验证与交付

自动化检查必须覆盖实际业务回归；不能只断言某段源码或文件存在。静态合同可作为补充，不能替代行为与浏览器检查。修改公共组件后检查其所有调用入口。

默认执行 npm test、npm run build、check:manifest、check:project、check:collaboration，以及受影响专项合同。合并阶段也不能跳过失败测试、删除保护断言或把回归测试改成接受错误行为。

浏览器最小验收覆盖：目标入口 → 其他入口 → 返回；检查导航、输入、选中态、弹窗关闭、长名称、头像与 AI 标。表单需实际保存再读取；输入需中文输入法、粘贴、编辑；任务需跨项目隔离。记录目标 SHA、预览 URL、视口与实际结果。

用户明确要求不测试时遵从，只做必要构建并说明未验收。不得把构建或 Vercel 部署成功表述为功能通过。不得用这种未验证状态宣称“无规范破坏”或“全部补齐”。

Preview 只用于评审；小改动按 CONTRIBUTING.md 允许直接推送 main，不重复索要发布确认。复杂改动与上游同步保留 PR 及人工确认。报告分别说明本地修改、分支/main 推送、Preview/Production 部署和浏览器验收状态。
