# IM 暗色适配规范

2026-09-16 建立。适用于聊天区内的气泡、引用卡、系统提示等由 Octo-Web IM 内核渲染的元素。
实现位于 `prototype/057-gds-dark-tokens.css`；浅色为默认且不在该文件内，所有规则必须限定在 `:root[data-theme="dark"]` 作用域。

## 1. 为什么 IM 区需要单独一份

Eva 的暗色通过 `057` 重指语义 token 实现：业务 CSS 只要消费 `--eva-*` / `--gds-*`，切主题即自动生效。

但聊天区是 Octo-Web IM 内核，它消费的是自己的 `--wk-*` / `--semi-*` 命名空间，另有大量直接写死的浅色值（`#fff`、`#1c1c230a`、`rgba(28,28,35,.8)` 等），**不经任何 CSS 变量**。这两套体系互不相通，因此 IM 区的每一个表面都要在 `057` 里显式补映射，不会自动跟随。

这与 AGENTS.md「GDS 适用范围是个人 Eva 体验，团队 IM 以 Octo-Web 为标准」的边界一致——暗色适配正是在这条边界上断开的。

## 2. 三条必须遵守的原则

### 2.1 遮罩翻转：交互态是叠加，不是换色

GDS §3.4 规定 hover/pressed/disabled 由「黑透明」翻转为「白透明」。

浅色的交互态普遍是往白底上叠黑（变暗），暗色必须反过来往暗底上叠白（变亮）。**直接给暗色挑一个新色值是错的**——很容易挑到比静态更暗的值，导致 hover 时元素反而沉下去，语义颠倒。

推荐写法是让「叠加」在 CSS 里就是叠加，而不是靠人工算出结果色：

```css
:root[data-theme="dark"] .ch-refcard:hover {
  background-color: var(--eva-c-neutral-750);
  background-image: linear-gradient(var(--eva-overlay-hover), var(--eva-overlay-hover));
}
```

这样 hover 必然比静态亮，不依赖选值是否正确。

### 2.2 半接管比不接管更危险

最常见也最严重的缺陷形态是**只接管了一半**：文字色被 Eva token 接管、表面色没接管（或反之）。

不接管时浅色两边自洽，至少还能读；半接管会直接产生白字白底。本轮实测到的三例：

| 元素 | 表面 | 文字 | 结果 |
|---|---|---|---|
| `.ch-refcard__tx` | 未接管，仍 `#fff` | 已接管为近白 | CR **1.07** |
| `.ch-refcard__ic` | 未接管，黑 5% | 未接管，黑 62% | CR **1.00** |
| `.wk-msg-system-tag` | 已接管为 `#1a1a1a` | 未接管，黑 40% | CR **1.01** |

**给任一 IM 元素补暗色时，必须把该元素的表面、边框、文字、图标、以及全部交互态一次补齐**，不能只改看起来最扎眼的那一项。

### 2.3 必要小字号走 accessible 档，不用 muted

GDS §14 区分 Fidelity 与 Production 两种模式：`muted`（暗色 `#939393`）只给占位、时间、非关键状态；**承载实际信息的小字号必须改用 `secondary-accessible`**（暗色 `#b0b4bd`）。

实测差距明显：在卡片面 `#313131` 上，`muted` 为 4.23（未达 AA 4.5），`secondary-accessible` 为 6.26。

判断依据是内容而非字号——「项目 · 类型 · 负责人 · 截止」是必要信息，走 accessible；尾部装饰箭头是纯装饰，留在 muted。

## 3. 各元素的明暗对照

以下为现行实现，浅色列是 vendor 原值（未改动），暗色列是 `057` 的映射。

### 3.1 消息气泡

| 项 | 浅色 | 暗色 |
|---|---|---|
| 收到（incoming） | `#f2f2f2` | `--eva-c-neutral-750` `#313131` |
| 发出（outgoing） | `#dce9ff` | `#1e3a63` |
| 分隔线 | — | `--eva-c-neutral-700` |

收到气泡取 `#313131` 的理由：它等于画布 `#242424` 叠加 `--eva-overlay-hover`（白 6%）后的实色，与左侧列表 hover 属同一「画布之上的抬升层」，不引入新色阶。

与画布对比 1.19（原 `#2a2a2a` 仅 1.08，气泡轮廓消失）。**不可再往上调**：`#343434` 起，收到气泡与发出气泡 `#1e3a63` 的对比会掉到 1.0x，两类气泡开始糊在一起，丢失收发区分。

### 3.2 引用卡 `.ch-refcard`（任务 / Loop / 文件等）

| 项 | 浅色 | 暗色 |
|---|---|---|
| 静态底 | `#fff` | `--eva-c-neutral-750` |
| 边框 | `rgba(28,28,35,.1)` | `--eva-border-subtle` |
| hover | 叠黑 2% | 叠 `--eva-overlay-hover`（白 6%） |
| hover 边框 | `#1c1c2338` | `--eva-border-default` |
| 图标槽底 | 黑 5% | `--eva-overlay-hover` |
| 图标槽前景 | `#1c1c239e` | `--eva-text-secondary` |
| 标题 `__nm` | `#1c1c23` | `--eva-text-primary` |
| 元信息 `__mt` | `#1c1c2380` | `--eva-text-secondary-accessible` |
| 来源 `.src` | `#1c1c23b8` | `--eva-text-secondary` |
| 尾部箭头 `__act` | `#1c1c2359` | `--eva-text-muted` |
| 锁定态 `--locked` | 更淡底 + 虚线 | `--eva-surface-subtle`（下沉）+ 保留虚线 |
| 锁定 hover | 压回静态 | 压回静态 |
| 锁定标题 | `#1c1c238c` | `--eva-text-secondary` |
| 卡内按钮 `__ask` | 白底 + 描边 | `--eva-surface-primary` + `--eva-border-subtle` |
| 按钮禁用 | 叠黑 4% | `--eva-overlay-hover` + `--eva-text-muted` |

暗色下卡片**靠可见描边界定边界**，不靠亮度——这是暗色比浅色更稳的做法。

锁定态在暗色下是**下沉**而非抬升：浅色用「更淡」表达不可用，暗色对应的是更暗。

### 3.3 「创建了子区」卡 `.wk-thread-created-card`

| 项 | 浅色 | 暗色 |
|---|---|---|
| 底 | `#1c1c230a`（黑 4%） | `--eva-overlay-hover`（白 6%） |
| hover 底 | `#1c1c230f`（黑 6%） | `--eva-overlay-pressed`（白 9%） |
| **左竖线 4px** | `rgba(28,28,35,.8)` | `--eva-c-blue-300` `#93b5ff` |
| 参与者 | `#1c1c2399` | `--eva-text-secondary-accessible` |

左竖线未改为中性灰，而取提亮蓝：这条 4px 竖条是该消息类型的**身份标识**，浅色下用近不透明黑本身就在做强调。暗色取 `#93b5ff` 后与卡内「子区名称 · N 条回复」链接同源，装饰条与语义对齐，而不是退化成普通分割线。

### 3.4 系统提示胶囊 `.wk-msg-system-tag`

| 项 | 浅色 | 暗色 |
|---|---|---|
| 底 | `#f2f3f4` | `--eva-surface-subtle` |
| 文字 | `rgba(28,28,35,.4)` | `--eva-text-secondary-accessible` |
| 关闭按钮 | `#1c1c2399` | `--eva-text-muted` |
| 关闭 hover | `#1c1c23` | `--eva-text-primary` |

底色保持「比画布略下沉」的关系：浅色 `#f2f3f4` 暗于白画布，暗色 `#1a1a1a` 暗于画布 `#242424`，明度关系一致。

### 3.5 @提及

`mention-entity` 在暗色下取 `--eva-c-blue-300`。填充蓝 `#6d98f7` 实测 4.07 略低于 AA，按 §3.4「链接/图标提亮」取链接档蓝。

### 3.6 消息输入框（2026-09-18 补）

适用三处：Eva 同学 `.eva-composer`（个人页 composer）、我的消息 / 我的 Agent `.wk-messageinput-card`（IM 输入框）。

| 项 | 浅色 | 暗色 |
|---|---|---|
| 底 | `#ffffff`（不变） | `--eva-surface-paper` `#2a2a2a`（原与画布同为 `#242424`） |
| 静态边框 | `#dbdbdb`（不变） | `--eva-border-faint`（白 6%，原 `#4a4a4a`） |
| 聚焦边框 | `--eva-border-focus` `#1563eb` | `#93b5ff` |
| 聚焦光环 | 2px `rgba(21,99,235,.08)` | 2px `rgba(109,152,247,.12)` |

**抬升的依据**：实测三页输入框底与画布 ΔL\*=0.00，整块「陷」进画布。浅色靠白底上的 `#dbdbdb` 描边撑住边界；暗色描边降到 `#4a4a4a` 后已托不住，且无底色差或投影。输入框是浮于会话画布之上的常驻操作面，按 GDS §3.4「层级用中性阶表达，越靠上越亮」在暗色取比画布高一档的 `surface-paper`（ΔL\*≈2.9）；浅色画布已是最亮的白，抬升只能继续由描边表达，故浅色仅补齐激活态、底色不动。

**两个配套约束**：

1. **暗色描边随抬升降档**：既有面就不需要 `subtle` 级描边，双重强调会让输入框显得突兀。降为 `faint` 后由面本身承担边界。
2. **描边规则必须用 `:not(:focus-within)` 限定**：暗色覆盖规则带 `:root[data-theme="dark"]` 前缀后特异度为 (0,3,0)，会压过 vendor/051 的 `:focus-within` (0,2,0)，导致暗色下聚焦不变蓝。聚焦态的边框色与光环一律由 `:focus-within` 规则负责，暗色层不得与其竞争。

**Eva 同学 composer 的激活态载体**：`.eva-composer` 原先没有 `border`，051 的 `:focus-within { border-color }` 无处可施，聚焦无任何反馈（可访问性缺陷）。已在 048 补 1px 常驻描边（`box-sizing:border-box` 防尺寸跳动），聚焦态补 2px 光环，与 IM 输入框同一契约。

**中栏色差同日裁决（`--eva-conversation-rail-surface` = `#222222`）**：三栏由左到右「由深到浅」递进（浅色 `#f5f6f8 → #fdfdfd → #ffffff`），暗色同向取 `#1a1a1a → #222222 → #242424`。**不可取比工作区更亮的值**——那会让中栏跳到三栏最亮端，递进变成「深→最亮→中」。GDS §3.4「越靠上越亮」讲的是 Z 轴高程（浮层 vs 底层），三栏是同一平面的并列分区，不适用该原则。列内标题栏（`.eva-rail-header`）必须与中栏主体同色，否则同一列上下两截色。

## 4. 已知偏离与待办

### 4.1 对 GDS §3.4 字面值的有意偏离

`--eva-border-faint` 未采用规范字面的实色 `#2A2A2A`，改为 `rgba(255,255,255,.06)`。

原因：§3.4 把同一个 `#2A2A2A` 同时定为「次级边框」与「抬升面」，两者撞色。实测 `#2A2A2A` 落在 `#242424` 面上 ΔL\*=2.9（浅色同档为 6.3），基本不可见，导致卡片描边、表格线、菜单边框在暗色下集体消失。改为白 6% 后，在 `#1a1a1a` / `#242424` / `#2a2a2a` 上分别为 ΔL\*≈6.8 / 6.2 / 5.9，与浅色对齐，且永远相对所在面成立。

**这是规范自身的缺陷，须作为规范修订项反馈给设计方**，不是实现层的自由选择。

### 4.2 两套规范冲突处的立场

`--eva-action-primary` 暗色取 EvaMate `blue/400` `#6d98f7` + 近黑前景，而非 GDS §3.4 的「填充锁死 `#1563EB` + 白字」。这是按用户指定的「EvaMate 优先」。若验收要退回 GDS 蓝，只需改 `057` 中 action 段的 4 行，但会全局影响所有经 `--eva-action-primary` 派生的按钮与选中态。

### 4.3 浅色遗留缺陷（本轮未改）

`.wk-msg-system-tag` 在**浅色**下 CR 仅 **2.44**（`rgba(28,28,35,.4)` 压在 `#f2f3f4` 上），属 vendor 原生缺陷，与暗色无关。本轮只修暗色，浅色是否一并提到 AA 待产品确认。

### 4.4 未验证的元素

带 `WS-1` 编号、迷你图表图标与右侧 agent 胶囊的那类卡片，在当前演示数据中没有实例，未做实测，暗色适配状态未知。

## 5. 验收方法

静态读源码不足以判断，必须实测合成色。要点：

- **按 alpha 合成后再算对比度**。多数 vendor 值是半透明的，直接拿 `color` 与 `background-color` 比会得出错误结论。
- **切主题后要把鼠标移开再测静态态**，否则量到的是 hover 值。本轮就因此一度误判浅色被改动。
- 每个元素至少覆盖：静态、hover、以及该元素存在的禁用/锁定态。
- 确认 hover 在暗色下**比静态亮**，而不只是「变了」。
- 改完后扫描 `057`，确认没有规则泄漏到 `[data-theme="dark"]` 作用域之外（浅色必须零改动）。

主题切换须走 `window.EvaTheme.apply('dark'|'light'|'system')`。直接写 `documentElement[data-theme]` 会被 `059-theme-controller.js` 的 MutationObserver 纠回用户档位。
