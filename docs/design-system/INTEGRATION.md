# Eva 设计规范整合说明

本目录并存两份来自客户的设计资料。两者来源、职责和完整度不同，不做文件级覆盖或内容拼接。

## 规范分工

| 范围 | 权威来源 | 使用规则 |
| --- | --- | --- |
| 颜色语义、Light/Dark、排版、间距、圆角、边框、效果、图标尺寸、动效 | `evamate-0.3.0/` | 作为 Foundations 层；产品代码通过项目语义变量或兼容映射消费，不直接复制 Primitive 色值 |
| 1200 × 800、260/940、776、390/810 页面骨架 | `evamate-0.3.0/layout-contracts.json` | 新包为机器合同，旧包参考图继续提供视觉证据 |
| 首页、输入、运营、生成中、完成态、技能选择六种状态 | `gds-for-ai2.0/` | 继续使用旧包的页面状态合同和六张参考图 |
| 组件结构、变体、状态和素材 | `gds-for-ai2.0/components.json` 与现有项目组件 | 新包明确不包含组件，不能据此重造组件或删除现有合同 |
| Eva 产品语义、身份、IM、项目颜色、路由和权限 | 根目录 `AGENTS.md` 及对应业务规范 | 设计包不能扩大或改写产品能力与数据边界 |

## 冲突顺序

1. 用户当前明确决定。
2. 根目录产品与工程规范。
3. 当前目标页面已经确认的设计和交互。
4. EvaMate 0.3.0 Foundations MUST 与布局合同。
5. GDS for AI 2.0 的组件合同、页面状态和参考图。
6. 两份包内标记为建议或推导的内容。

同一基础视觉值发生冲突时优先采用 EvaMate 0.3.0；组件结构或页面生命周期只有旧包有证据时继续采用旧包。不得把新包 `components: false` 解释为允许自由设计组件。

## 工程接入边界

- 两份客户原包保持独立，便于追踪来源和运行各自校验器。
- `evamate-0.3.0/tokens.json` 是新包的源令牌，`tokens.dtcg.json` 与 `tokens.css` 是生成产物；不要手改生成产物。
- 在产品源码迁移完成前，不全局加载 `tokens.css`，也不批量替换现有 `--eva-*`、Semi 或 Octo 变量。
- 新令牌通过显式兼容层逐页接入；项目 `colorKey`、状态色与 Eva 品牌色继续保持独立业务语义。
- 现行产品已接入 Light/Dark，采用王岩在 main 中维护的主题与公共语义变量。设计包校验不代替对应页面的深色浏览器验收。
- 视觉改动仍须使用本地 HTTP 和真实浏览器，对照现有页面、旧参考图及用户确认截图验收。

## 验证

```bash
node docs/design-system/validate-all.mjs
```

联合校验会分别执行两个上游校验器，并检查整合清单中的路径、共同基准几何和品牌主蓝。它只验证设计资料完整性，不代替产品页面的浏览器验收。
