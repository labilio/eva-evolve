# 分身身份与所属人展示规则

2026-09-09 用户确认，覆盖此前多分身、自定义名称／头像和灰色 `@主人` 的规则。

- 每位真人可以没有分身，最多一个。名称由稳定 ownerId 对应的真人姓名推导为「xxx的 AI 分身」，不可独立修改；默认以圆形 Eva Logo 为主图（单张、不叠加角图），主人可通过身份资料卡在本人账号下更换主图，恢复默认即回到 Eva Logo，姓名仍不可修改。
- 公共名称与头像分别调用 `EvaAIIdentity.cloneName(owner)`、`cloneAppearance(owner)`，头像仍由 `EvaAIIdentity.avatar` 渲染：默认 Eva Logo 为单张圆形主图，自定义主图同样保持单张。分身头像只有一个数据源：成员业务数据中的分身记录（按稳定 ownerId 查找），通讯录、成员、消息与我的 AI 全部经 `cloneAppearance` 读取，不保留第二份副本。
- 个人助理不是分身：默认以同一圆形 Eva Logo 为主图（单张、不叠加角图），可在共享编辑器内自选 emoji／图标替换主图，也可由主人从身份资料卡上传图片替换；数字员工保持单张圆形主图。
- 人类与 AI 仍是独立身份；不改变项目访问权限、添加成员规则和 AI 发言触发条件。个人助理、数字员工不适用本次单分身限制。

| 入口 | 展示 |
| --- | --- |
| 会话标题、消息署名 | 固定分身名＋公共 AI 标，不附加 `@主人`；不使用其他颜色保留同类附加信息 |
| 添加成员、群／项目成员、提及候选 | 固定头像＋分身名＋AI 标，不再显示主人第二行 |
| 紧凑会话列表、头像网格、已选标签 | 同一公共身份，不重复所属人 |
| 身份资料卡 | 保留可点击的「所属人：姓名」及真人头像，可以进入真人资料并返回（查看与跳转逻辑见下节） |
| 正文提及 | 仍是真实的 `@xxx的 AI 分身`，不额外提及所属真人 |
| 输入提示 | 继续使用 `evaIMPlaceholder`，不追加所属人 |

`ownerLabel` 仅负责资料卡的所属人文本；标题、消息、候选中的调用和专用 CSS 已退出。资料卡解析、历史消息和结构化提及按身份 ID 读取，不通过名字猜测归属。

## 查看与跳转逻辑（2026-09-24）

**能不能看：始终可看。** 所属人（真人头像与姓名）在所有宿主、所有类型的身份资料卡上正常展示；不隐藏归属，也不降级为没有归属的说明文案。

**能不能跳转：始终可跳。** 任意宿主中点击所属人，都在同一张身份资料卡内替换为主人的真人资料卡，并提供返回；跳转深度不超过一层（分身 → 主人为止，主人资料卡内不再提供下一跳）。跳转只发生在同一张卡内替换内容，不叠开新弹窗、不跳转页面。

**导航与动作分离。** 查看与跳转不按宿主或身份做条件分支；跳转本身不授予、也不改变任何动作权限——能不能发消息、能不能执行管理操作，仍由目标身份在对应宿主的既有规则决定，不因“从分身卡跳来”而新增或扩大入口。例如他人的云端分身不因被查看资料而获得私人对话权限，仍保留群内 @ 协作说明。归属一律按稳定 ownerId 解析，不按显示名称猜测。

产品依据（2026-09-24 调研）：

- 归属可见是主流做法：飞书机器人资料卡公开展示开发者；Slack 应用标注 made by；微信公众平台资料页展示账号主体；Teams 应用卡展示发布者。Discord 隐藏 bot owner 属于匿名第三方 bot 场景，不适用于以组织内同事为主人的 Eva 分身。
- 归属可跳有成熟先例：飞书帮助文档写明“点击机器人的头像，查看并联系其开发者”；Teams／M365 资料卡 Organization 支持沿汇报线在同一张卡内跳转，并带会话内导航历史；Discord 用户资料弹窗可从共同好友／共同服务器继续打开他人资料。
- “展示了却不可点”被系统性回避：凡引用“有产品内资料页的人”的入口（Teams 组织链、Discord 头像与成员列表、微信群成员、飞书开发者、GitHub／Jira／Linear 的人员引用）都可交互；纯文本归属只出现在被引用对象没有产品内资料页时（Slack made by、Teams 发布者名、微信账号主体、Google Drive 的 Owner 行）。因此展示主人头像与姓名时必须可进入。

## 旧数据兼容

- 我的 AI 保留原 `persona-initial`（没有时保留首个分身）作为唯一身份；额外身份建立 ID 别名，旧会话的 ID、消息与会话草稿保留。
- 额外身份的未发送草稿分别恢复为该分身下的「未发送草稿」会话，不覆盖主分身草稿；旧配置备份在本地业务状态中，不作为另一可用分身。
- 成员数据按稳定 ownerId 合并多分身，保留原有项目／群成员关系和角色关系，不给其他真人增加访问权限。旧链接仍可解析所属人的唯一分身。
- 分身配置保存及来源同步仍不接受改名；并发创建也只能成功一次。分身头像由成员业务数据中的分身记录唯一提供，只有主人本人可以修改，不写入分身配置，也不产生第二份副本。
- 所有数据仍为浏览器本地原型数据，本次没有扩大 Supabase 职责。
