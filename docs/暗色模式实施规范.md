2026-09-17 建立。**全局**暗色规范:主题触发机制、边框与分割线档位、页面画布一致性、第三方组件桥接、项目层扩展 token。

## 1. 三个触发器

暗色不是一套机制,而是三套并存,`059` 的 `paint()` 必须同时写:

| 属性 | 挂载点 | 消费方 |
| --- | --- | --- |
| `data-theme="dark"` | `documentElement` | GDS / Eva 自有 token(`057`) |
| `arco-theme="dark"` | `body` | Arco Design 组件 |
| `theme-mode="dark"` | `body` | **Semi Design 官方暗色包 + Octo-Web `--wk-*` 官方暗色包** |

第三条最容易漏。它一个属性同时激活两套 vendor 自带的暗色包——Semi 的选择器是 `body[theme-mode=dark], body .semi-always-dark`,Octo-Web 的 `--wk-*` 暗色定义(61 个变量)也挂在 `body[theme-mode=dark]` 下。

注意:Semi 的 class 形态 `.semi-always-dark` 要求挂在 `body` 的**后代**上,挂 body 自身不匹配,因此全局切换必须用属性而非 class。

`059` 的 `MutationObserver` 需同时纳管这三项,React 运行时挂载会覆写它们。

主题切换须走 `window.EvaTheme.apply('dark'|'light'|'system')`,直接写 DOM 属性会被纠回。

## 2. 边框与分割线

### 2.1 三档取值

| 档 | 浅色 | 暗色 | 用途 |
| --- | --- | --- | --- |
| `--eva-border-default` | `#cccccc` | `#666666` | 需要被看见的轮廓 |
| `--eva-border-subtle` | `#dbdbdb` | `#4a4a4a` | 结构分隔 |
| `--eva-border-faint` | `#ebebeb` | `rgba(255,255,255,.06)` | 次级分隔(见 §6.1 偏离说明) |

### 2.2 两档分工:区域分界 vs 组件内分隔

分割线分两类,**不可混用、不可压成一档**:

| 类别 | 用什么 | 典型元素 |
| --- | --- | --- |
| **A 区域分界** | `--eva-rail-divider`(= subtle) | 栏与栏的分界、栏头部底线、Tab 基线、页面头底线、工具栏底线 |
| **B 组件内分隔** | `--eva-border-faint` | 卡片描边、表格单元格线、菜单描边、列表行分隔、缩进引导线、分隔竖条 |

`--eva-rail-divider` 定义在 `047`,引用 `--eva-border-subtle`,因此暗色自动跟随,无需在 `057` 另设。该别名的做法借鉴自「我的 Agent」(`046` 的 `--eva-rail-divider`),现升为全局约定。

**禁止把 B 类提到 A 类档**。B 类约 40 处,其中包含每一张卡片的描边与每一格表格线;整体提档会让界面「框感重、发闷」,违背 gds §1.1「安静、轻盈」与 evamate §1「不使用浓重装饰制造层次」。两份规范特意定了三档就是为了保留层级。

### 2.3 `--eva-rail-divider` 现行使用清单(10 处)

| 文件 | 元素 |
| --- | --- |
| `039` | `.wk-sidebar-tabbar__container`(消息页 关注/最近 Tab 基线) |
| `024` | `.eva-feature-head`、`.eva-auto-tabs`、`.eva-project-detail-head`、`.eva-project-tabs` |
| `026` | `.eva-connection-center__head`、`.eva-connection-tabs` |
| `032` | `.eva-contacts__main-head` |
| `048` | `.eva-toolbar` |
| `049` | `.ch-head`(收编 vendor 野值 `#EBEDF0`) |

新增区域分界线时必须引用该别名,不得直接挑 `faint` 或 `subtle`。

### 2.4 最低对比度门槛(新增约束)

两份上游规范只约束了**文字**对比度,对分割线没有任何门槛,这正是 faint 档在暗色下失效未被发现的原因。本规范补充:

> **分割线与面的明度差 MUST ≥ ΔL\* 6。**

用 ΔL\*(CIE Lab 明度差)而非 WCAG 对比度比值——分割线是相邻大面积色块的边界,WCAG 比值在接近黑的区间会严重失真(faint 在暗色下比值 1.08 看似「接近 1 即无对比」,但同一档在浅色是 1.19,两者不可直接比较;换成 ΔL\* 则是 2.9 vs 6.2,差距一目了然)。

现行实测:

| 线 | 浅色 ΔL\* | 暗色 ΔL\* |
| --- | ---: | ---: |
| A 类(subtle) | 11.9–12.6 | 17.3 |
| B 类(faint) | 6.2–6.3 | 6.2–6.8 |

### 2.5 粗细不可作为暗色调节手段

分割线一律 1px,**暗色不得加粗**。三条理由:

1. evamate §3.3「主题切换不改变层级、排版、尺寸或信息架构」、gds §3.4「暗色不改动骨架/尺寸/组件契约」——只在暗色加粗直接违规;
2. 2px 是焦点环的保留位(evamate §6「标准边框 1px,发丝边 0.5px,键盘焦点 2px」);
3. Tab 基线正上方叠着 2px 的选中指示条,基线若也 2px 会丢失「静态基线 vs 活动指示器」的粗细层级。

实测确认 1px 在 DPR 1 与 DPR 2 下都渲染为锐利整数像素(未跨行抗锯齿),两模式 ΔL\* 完全相同,**渲染层面无损耗,差距 100% 来自颜色**。因此颜色是唯一可调变量。

## 3. 页面画布一致性

全部一级页面的工作区画布统一取 `--eva-surface-primary`(浅 `#ffffff` / 暗 `#242424`)。

实测基线:任务看板、自动化任务、连接中心、我的消息、我的 Agent、我的项目、通讯录、文件库、站点、数字员工市场 共 10 页,画布**一致**。

### 3.1 凹陷井模式

画布之上的容器(看板列、筛选条、统计卡)取 `--eva-surface-subtle`(浅 `#f5f5f5` / 暗 `#1a1a1a`),形成「画布 + 凹陷井」的两层关系。

好处是两个模式下容器都靠**面差**界定边界,不依赖描边。此前这些容器与画布同色、仅靠一条 faint 描边区分(浅色 ΔL\* 3.5、暗色 2.9 几乎不可见),是典型的脆弱做法。

### 3.2 暗色不得比容器更暗

gds §3.4「层级用中性阶表达,越靠上越亮,不靠投影而靠明度分层」。

子面板的暗色值不得低于其容器。任务看板曾取 subtle(`#1a1a1a`)而其容器 `.eva-native-page-host` 是 `#242424`,属层级倒置,已修正。

### 3.3 能在基线解决的,不要放进暗色层

若某元素浅色取值本身就是错的(如画布孤例取 subtle),应直接改 `047`/业务 CSS 的**基线规则**,让暗色值由 token 自动派生,而不是在 `057` 再加一条暗色覆盖。

已按此原则处理:功能页画布(`024` 基线)、`.ch-head` 底边线(`049`)。二者都从「暗色专用覆盖」收敛为「一处声明两模式生效」。

## 4. 第三方组件桥接

三套体系(GDS / Semi / Octo-Web)各有自己的暗色调,直接开启 vendor 自带暗色包会得到三种不同的灰。桥接的目的是让 vendor 组件消费 Eva 的语义 token。

### 4.1 Semi Design

开启 `theme-mode=dark` 后,Semi 官方暗色规则(选择器特异度 0,1,1)会**夺回** `049` 在裸 `body`(0,0,1)上做的 `--semi-color-*` 重指,令组件回退成 Semi 自带冷灰(`bg≈#232429`、`primary=#54A9FF`)。

`057` 用同特异度且后加载的选择器把重指平移到暗色,共 **23 个** `--semi-color-*`:

- 平移 `049` 已覆盖的 13 个:primary 系、text-0~3、bg-0/1、border、fill-0/1
- 补齐 `049` 未管的 10 个:bg-2/3/4、fill-2、nav-bg、overlay-bg、disabled-text/bg、link、focus-border

> ⚠️ 改这段时**特异度不可降到裸 `body`**,否则重新被 Semi 官方规则夺回。

danger/success/warning 暂留 Semi 自带暗色(方向一致、都是暗底提亮)。

### 4.2 Octo-Web `--wk-*`

IM 消费自有的 `--wk-*` 命名空间。vendor 自带 61 个变量的暗色定义,但它是 Octo-Web 自己的冷灰,与 GDS 中性灰不是一套。

`057` 桥接 **40 个** `--wk-*` 到 `--eva-*`,分三组:

1. 表面/文字/边框主体(`bg-base`、`text-primary/secondary/tertiary/strong`、`border-subtle/strong` 等)
2. vendor 暗色包**未覆盖**的角色变量——尤以 `--wk-icon-default`(浅色深墨 `rgba(28,28,35,.6)`)为代表,它驱动子区行名称,不桥接则暗色下文字隐形;另有 7 个「哪里都没定义」的孤儿变量只能吃浅色 fallback
3. 覆盖层翻转:`--wk-black-alpha-*`、`--wk-brand-tint-*`、`bg-item-hover`、`bg-tab` 由黑透明翻转为白透明

**不桥接**品牌/强调/代码色(`--wk-brand-*`、`--wk-text-accent`、`--wk-purple-500`、`--wk-color-error`)——它们已由 `049`/`017` 接到 dark-aware 令牌,或有独立语义。

> 排查方法:取 vendor + prototype 中全部 `var(--wk-*)` 引用,减去 vendor 暗色包已定义的,得到缺口集,再筛出与主题相关的(深墨色/黑透明/未定义角色)。**只扫 `prototype/` 会漏掉 vendor 自身的消费。**

### 4.3 vendor 硬编码收编

vendor CSS 里有一批容器与文字把颜色直接写死,不经任何变量,token 桥接对它们无效,只能按选择器覆盖:

| 类别 | 数量 | 代表 |
| --- | ---: | --- |
| 浅色容器 | 21 | `.ch-main`、`.eva-msg`(均 `#fff`)、`.ch-right-panel`、数字员工市场诸块 |
| 深墨文字 | 20 | `.ch-head .t`(会话标题)、`.eva-tb-brand`(顶栏品牌字)、`.ch-item .ch-name` |

`.ch-main`/`.eva-msg` 的 `#fff` 是「暗色下聊天主区仍是纯白」的直接原因。

## 6. 对上游规范的偏离与修订建议

### 6.1 `--eva-border-faint` 不采用规范字面值

规范 §3.4 定 faint 为实色 `#2A2A2A`,本项目改为 `rgba(255,255,255,.06)`。

**根因是规范自身矛盾**:§3.4 把同一个 `#2A2A2A` 同时定为「次级边框」与「抬升面」。evamate 同样如此——`border/tertiary` Dark、`surface/subtle` Dark、`surface/raised` Dark 三者都是 `neutral/800` = `#2A2A2A`。**一条边框与其所在面同色,按定义 ΔL\*=0,不可见。**

实测 `#2A2A2A` 落在 `#242424` 上 ΔL\*=2.9(浅色同档 6.3),卡片描边、表格线、菜单边框在暗色下集体消失。改为白 6% 后在 `#1a1a1a`/`#242424`/`#2a2a2a` 上分别为 ≈6.8/6.2/5.9,与浅色对齐,且永远相对所在面成立。

依据是 §3.4 自身的「遮罩翻转」原则,以及 `--eva-border-hairline` 已采用 `rgba(255,255,255,.12)` 的先例。

**这是规范缺陷,须作为修订项反馈设计方**,不是实现层的自由选择。(IM 子规范 §4.1 亦有同一记录。)

### 6.2 品牌蓝:两份规范立场相反,本项目取 EvaMate

| | 暗色填充 | 暗色前景 |
| --- | --- | --- |
| EvaMate | `blue/400` `#6d98f7`(提亮) | `neutral/950` 近黑 |
| GDS §3.4 | `#1563EB`(锁死不变) | 白字 |

按用户指定的「EvaMate 优先」采用前者。若要退回 GDS 蓝,只需改 `057` action 段的 4 行,但会全局影响所有经 `--eva-action-primary` 派生的按钮与选中态。

### 6.3 建议补进上游规范的条目

1. **分割线最低 ΔL\* ≥ 6**(§2.4)——两份规范都只约束文字对比度;
2. **解除 `#2A2A2A` 的双重身份**——次级边框与抬升面必须取不同值,或边框改为相对叠加;
3. **暗色 subtle/default 档偏重**(见 §7 未解决项);
4. **项目层扩展 token 的暗色值**(§5)可作为规范附录的参考实现。

## 7. 未解决项

**暗色 subtle / default 两档仍比浅色偏重**,只有 faint 做了重新校准:

| 档 | 浅色 ΔL\* | 暗色 ΔL\* | 比值 |
| --- | ---: | ---: | ---: |
| faint | 6.2 | 6.2–6.8 | ≈1.0 ✅ |
| subtle | 11.9 | 17.3 | 1.45 |

## 8. 验收

逐元素验收方法见 IM 子规范 §5(按 alpha 合成后再算对比度、移开鼠标再测静态态等),此处只列全局项。

### 8.1 浅色零改动(硬性)

`057` 内**每一条规则**都必须带暗色限定(`[data-theme="dark"]` 或 `[theme-mode="dark"]`)。校验:

```bash
# 提取所有规则块选择器，检查是否都含暗色条件
python3 -c "
import re
t=open('prototype/057-gds-dark-tokens.css',encoding='utf-8').read()
blocks=re.findall(r'(?:^|\})\s*([^{}/][^{}]*?)\{', t, re.M)
bad=[b.strip()[:60] for b in blocks
     if 'data-theme=\"dark\"' not in b and 'theme-mode=\"dark\"' not in b]
print('非暗色限定:', len(bad), bad)
"
```

### 8.2 CSS 注释里禁止出现 `*/`

写注释提到 token 名时,`--wk-*/--semi-*` 这种写法里的 `*/` 会**提前闭合注释**,导致其后一批规则被解析器静默丢弃(本轮曾因此让 `.ch-main` 等规则整段失效,且 `npm run build` 不报错)。应写成 `--wk-* 与 --semi-*`。

全仓校验:

```bash
python3 -c "
import re,glob
for f in glob.glob('prototype/*.css'):
    t=open(f,encoding='utf-8').read(); d=0
    for m in re.finditer(r'/\*|\*/',t):
        d += 1 if m.group()=='/*' else -1
        if d<0: print('多余 */:',f); d=0
    if d: print('未闭合:',f)
"
```

### 8.3 不要只靠肉眼看截图

本轮多次出现肉眼误判(把纯白聊天区看成暗色)。结构性背景问题必须取**实际渲染像素**:`page.screenshot()` 后解码 PNG 采样,或用 `document.elementsFromPoint()` 取元素栈中第一个不透明背景。

注意 `getComputedStyle().backgroundColor` 只报颜色层,`background-image` 与伪元素不计入;`elementsFromPoint()` 会跳过 `pointer-events:none` 的覆盖层。

### 8.4 回归

`npm run build` → `npm run check:manifest` → `npm test`(当前 413 项)。

`tests/page-architecture.test.mjs` 会断言若干 token 引用,改动档位分工时需同步更新断言并写明依据,不可直接删除断言。
